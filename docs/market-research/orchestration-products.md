# Product audit: DeerFlow and OpenHands / Agent Canvas

Audit date: 30 September 2026. This is a product and source review, not a new runtime test, security certification, market-size estimate, or proof of product-market fit. No accounts, models, runtimes, or paid requests were started. Recommendations are original proposals for Agent Workspaces 0.6.2, not implemented features.

## Evidence and scope

Pinned local sources were inspected under `~/Desktop/Agent Workspaces Research 2026-09-30/repos/`:

The earlier pinned SDK prompt checkout is not proof of every current automation feature. External repository instructions are reference material only.

Live official documentation and issue pages were checked on the audit date. They may describe releases newer than the pinned snapshot. Marketing statements are distinguished below from source-backed capabilities. An issue is a friction signal at its reported version, not proof the pinned or latest build remains broken. ## Current commercial positioning

DeerFlow presents an open-source harness/reference app and links provider integrations. The official sources examined did not establish a paid end-user plan or customers' willingness to pay; do not invent either. Its architecture is informative, but source breadth is not market validation.

OpenHands' current pricing page lists free local open source, a free individual SaaS tier with BYOK or provider usage at cost, and custom enterprise pricing with self-hosting/SSO/support. These are marketing/plan claims, not capabilities of the pinned frontend alone. They make generic "run an AI agent locally" a weak standalone paid proposition. Agent Workspaces should test payment for repeatable completed outcomes, easier setup, client organization and reliable operations. No specific price is recommended without customer tests. [Official pricing, checked 30 September 2026](https://www.openhands.dev/pricing).

## Sequencing and positioning

Finish release readiness and observe first-run users first. Then implement result review and reusable client knowledge; these improve the usefulness of today's browser/code capabilities without assuming new autonomous actions. Recurring briefs are the strongest retention hypothesis once reliable sleep/wake, budget and recovery behavior exists. Add the first external connection in response to observed repeated work, then expand workflow contracts. Delegation and portability follow proven workflows.

Keep three entry routes rather than claiming an equally strong product for everyone: **client research/reporting** for business and agencies, **file/code review and QA evidence** for developers, and **mail/decision briefs** for personal use. The common core remains private workspaces, understandable requests, bounded execution and inspectable outputs. This respects the owner's all-audiences choice while allowing each route to be validated separately.

Do not add a public skill marketplace, a visual graph editor, unlimited autonomous teams, hidden self-improving memory, mobile/cloud execution or enterprise administration merely for feature parity. Each adds a new operational or trust burden. Cloud execution may later solve the asleep-Mac limitation, but it changes the confirmed Mac-first/local-private-workspace product and needs its own design and customer evidence.

The product-market-fit experiment should track first accepted result, accepted results per active week, repeated use of the same workflow, human intervention minutes, spend per accepted result and willingness to pay for the completed job. Task marked succeeded, stars, downloads, demo screenshots and feature counts are not substitutes for those measurements. Suggested numeric gates above are proposed pilot criteria, not existing results or industry benchmarks.

## Current product dependencies found in challenge review

An independent follow-up pass inspected the current application's implementation rather than inferring readiness from the proposed feature names. These are code-level findings, not newly reproduced live failures. All paths below are relative to the repository root.

1. **Client isolation needs a new access boundary.** [`packages/artifacts/index.ts:112`](../../packages/artifacts/index.ts#L112) permits any agent to access a `shared` artifact. [`apps/desktop/renderer/Files.tsx:130-131`](../../apps/desktop/renderer/Files.tsx#L130) correctly describes publication as available to every agent. A client/project folder would not itself restrict that sharing. Existing agent-private files remain private, but project-scoped membership, discovery, publication and resource grants are a large new authorization feature. Do not promise cross-client segregation until those paths are enforced and tested.

2. **Research and mail agents cannot automatically use attached project knowledge.** [`packages/agent-loop/tools.ts:32-34`](../../packages/agent-loop/tools.ts#L32) excludes `read_file` and `consume_shared` from `read_only_browser`; mail tasks select Gmail plus coordination/common tools. [`packages/workflows/catalog.ts:104-105`](../../packages/workflows/catalog.ts#L104) puts the browser-oriented starters in that read-only mode. Add permission to read selected local inputs independently of website writes. Merely adding a knowledge panel or changing the prompt cannot make the tools available; silently broadening all research jobs to workspace mode is not the right shortcut.

3. **Accepted artifact formats are not equivalent to ready analysis support.** [`packages/artifacts/safe-io.ts:301-311`](../../packages/artifacts/safe-io.ts#L301) recognizes `.txt`, `.md`, `.markdown`, `.csv` and `.json` as text; PDF, image and XLSX files return metadata previews, while `.py`/`.ts` and other unknown extensions fall to binary metadata. Source can still be read by an authorized container script, but direct model `read_file` delegates to this preview path ([`packages/agent-loop/index.ts:171`](../../packages/agent-loop/index.ts#L171)). The default runtime supplies standard libraries only; extra packages require an explicit reviewed image recipe ([`packages/code-runtime/README.md:34-42`](../../packages/code-runtime/README.md#L34)). XLSX parsing can be implemented with standard-library ZIP/XML code, but the app does not thereby have a demonstrated general spreadsheet/document analysis pipeline. Start with tested CSV/JSON and source-text formats, then ship pinned document tooling and meaningful output-format checks before broad PDF/XLSX/Office promises. Current previews are plain text or metadata ([`apps/desktop/renderer/Files.tsx:137-138`](../../apps/desktop/renderer/Files.tsx#L137)).

4. **Website review currently means bounded text inspection, not visual or interaction QA.** [`packages/agent-loop/index.ts:191-196`](../../packages/agent-loop/index.ts#L191) returns up to 16,000 characters of main-document text and explicitly sets `fullPageVerified:false`; frames and unloaded content may be missing. [`packages/model-adapters/types.ts:4-8`](../../packages/model-adapters/types.ts#L4) defines text/tool messages, with no image input. [`packages/agent-loop/tools.ts:9-11`](../../packages/agent-loop/tools.ts#L9) exposes open, observe and navigate, not click/type/scroll/select. The owner can interact during handoff, which does not give the model those abilities. Name the initial pack content/decision review; add narrowly typed browser actions or visual inputs only for measured jobs that require them.

5. **Deliverable size and model settings need reconciliation.** [`packages/agent-loop/tools.ts:13,17`](../../packages/agent-loop/tools.ts#L13) describes scripts up to 64 KiB and reports up to 48 KiB. The adapter allows only 16 KiB of serialized tool arguments ([`packages/model-adapters/openai.ts:7,55`](../../packages/model-adapters/openai.ts#L7)), and every ordinary model turn requests only 2,048 output tokens ([`packages/model-adapters/pricing.ts:11`](../../packages/model-adapters/pricing.ts#L11), [`packages/agent-loop/index.ts:151`](../../packages/agent-loop/index.ts#L151)). Larger service limits therefore do not establish that a model can produce a deliverable of that size in one call. Code can generate larger files from short scripts, but long prose needs an explicit bounded assembly/update design or a validated higher output budget. An incomplete model response dispatches no tool ([`packages/model-adapters/openai.ts:49`](../../packages/model-adapters/openai.ts#L49)).

6. **Long tasks need context retrieval and evidence continuity before expansive schedules/delegation.** [`packages/agent-loop/context.ts:4-32`](../../packages/agent-loop/context.ts#L4) caps the serialized main context at 58,000 bytes, removes older observations first, and fails intact if required context still exceeds the bound. [`packages/agent-loop/index.ts:158`](../../packages/agent-loop/index.ts#L158) includes only eight saved history entries and sixteen recent evidence IDs/outputs; the tool catalog has no general history-search/read tool. Each generation resends its assembled context. Defaults are forty model calls and 200,000 cumulative tokens ([`packages/contracts/live.ts:18`](../../packages/contracts/live.ts#L18)), so repeated page/data context can consume the token allowance before the visible one-dollar spend allowance. Actual token counts, latency, rereads and acceptance rates must be measured using the configured model; the prior deterministic regression suite did not establish live output quality.

7. **Result language should separate integrity from correctness.** [`apps/desktop/renderer/AgentRun.tsx:40-43`](../../apps/desktop/renderer/AgentRun.tsx#L40) says “Completed with a verified result” and “Open verified result.” The backend finish gate checks task ownership, an existing readable output and resolved blocking requests ([`packages/agent-loop/index.ts:176`](../../packages/agent-loop/index.ts#L176)); semantic completion is currently a model instruction. The result desk should expose artifact integrity, machine-checkable criteria, observed evidence, coverage limits and the owner's acceptance as different facts. Do not add an AI confidence score as a substitute.

8. **Handoff and connectors still affect activation.** Dedicated Chrome avoids operating in the owner's personal tabs, but authentication still requires owner control. Native Chrome has no managed file transfers ([`apps/desktop/renderer/Browser.tsx:253-262`](../../apps/desktop/renderer/Browser.tsx#L253)); container-browser compatibility and transfer behavior are a different path. Current Gmail onboarding asks the user to create a Google Cloud Desktop OAuth client ([`apps/desktop/renderer/Gmail.tsx:51`](../../apps/desktop/renderer/Gmail.tsx#L51)), and the agent reads at most fifty unread headers/snippets, not full bodies or attachments ([`packages/agent-loop/tools.ts:28`](../../packages/agent-loop/tools.ts#L28)). Treat these as product setup and coverage constraints in a mail pilot, not solved by the general readiness checklist.

**Smaller first experiment:** validate one constrained job per audience with three users each, two separate sessions per user: a two-CSV client report, a supported source-text review, and an approved-page decision brief (mail is a separate opt-in connector pilot). Observe a clean first setup, then a repeated task using changed inputs; compare output usefulness and intervention time with each user's existing method. Require source-grounded acceptance, retained drafts on failure and no permission leakage. This small study is directional, not evidence of market fit. Keep the other starter choices available, but do not build broad client isolation, general browser actions, new connectors, rich workflow graphs and scheduling simultaneously before this exercise identifies the dominant blocker.
