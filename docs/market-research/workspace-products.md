# Workspace product audit: Kortix/Suna and OpenAgents

Audit date: 30 September 2026. Compared against Agent Workspaces **0.6.2**, inspected from the current source. This is product research, not an implementation or a claim of product-market fit. No applications, paid models, credentials, live connectors or competitor runtimes were started during this audit.

## Main finding

The largest opportunity is to make a useful job easy to start, easy to review and worth repeating. Agent Workspaces already has unusual care around private agent environments, owner corrections, exact file versions, explicit sharing and bounded execution. Its present product surface is still limited: six brief-generating starters, a narrow Gmail reader, manually approved website sources, text/metadata previews and separate setup controls. A customer cannot yet reliably go from installing the app to a recurring, polished business deliverable without substantial assistance.

Kortix offers useful patterns for connecting existing business systems, turning repeat work into scheduled runs, reviewing changes and seeing cost. OpenAgents offers useful patterns for shared work, human workflow steps, actionable notifications and setup across multiple agents. These capabilities are evidence of competitive expectations, not evidence that copying them will create demand.

The best proposed positioning to test is: **a private workbench that turns your files, websites and connected accounts into reviewable, repeatable work, while you retain control.** Support business, developer and personal jobs through distinct starter packs; do not make every customer configure a general multi-agent system before receiving value.

## Public positioning, packaging and friction

Kortix currently advertises a free tier with 200 monthly compute credits and one project, a Team tier at **$40 per seat per month** with pooled credits and optional managed models, and enterprise deployment/governance. Treat this as the public offer on the audit date, not our target price or proof of willingness to pay. Its website positions the product around company workflows and existing systems. [Pricing](https://kortix.com/pricing).

OpenAgents describes a free/open-source workspace with direct underlying model-provider charges; the site positions shared conversations, files, browsers, workflows, routines and an inbox across devices. This makes a generic multi-agent workspace interface a weak standalone paid differentiator. Our proposed paid value should be reliable completed jobs, client separation, polished reviewed results and repeatable operation. This is an inference requiring customer validation. [OpenAgents FAQ](https://openagents.org/faq), [Workspace product page](https://openagents.org/workspace).

Important limits of the public claims:

- Kortix advertises a large connection catalog; configuring and testing every app was outside scope. Its channel page explicitly distinguishes default Slack, operator-enabled Teams and experimental email. A generic signed webhook is not a full bidirectional channel. [Connectors](https://kortix.com/connectors), [Channels](https://kortix.com/channels).
- Kortix's automation page says cron/webhook are the only types, while pinned `packages/manifest-schema/src/constants.ts:92` also includes `monitor`. Its connector policy source still documents legacy `allow_all` as the default, and the public connector page explains the same fallback. We should not import that default. Its change-request source permits an explicitly merge-granted agent to merge its own work, so “nothing merges itself” on marketing pages should not be treated as an unconditional platform invariant. [Automations](https://kortix.com/automations), [source constants](https://github.com/kortix-ai/suna/blob/7df56c8b3afafe1ef89e5f06e0fd29af10bca55d/packages/manifest-schema/src/constants.ts#L92), K3/K5.
- OpenAgents' FAQ has a shorter supported-agent list than its pinned README, which marks some adapters beta and explicitly says real-provider end-to-end validation is pending. Supported adapter count is not equivalent to equally reliable execution. Its workflow judge advances an agent step when no judge is available (`workflow.py:261–281`); our completion contract must stay evidence-backed. [README](https://github.com/openagents-org/openagents/blob/d46d087dca2279eac25414621e6af91bc8b3338b/README.md), [workflow fallback](https://github.com/openagents-org/openagents/blob/d46d087dca2279eac25414621e6af91bc8b3338b/workspace/backend/app/services/workflow.py#L261).

## Our current capability boundaries

These were verified in current source rather than inferred from the original planning documents:

- `package.json:3`: version 0.6.2. `apps/desktop/renderer/App.tsx:269`: local single-owner workspace.
- `packages/workflows/catalog.ts:5–65`: six built-in starters across business, development and personal jobs. `catalog.ts:95–119`: saved tasks use explicit inputs and base policies; code review has no automatic repository checkout; Gmail reads headers/snippets without mailbox writes.
- `packages/agent-loop/tools.ts:6–34`: actual available tools, exact-version sharing, read-only Gmail, offline code and policy-filtered capabilities. A generic connector catalog, arbitrary CRM operation and GitHub PR integration are not present.
- `apps/desktop/renderer/Files.tsx:137–140` and `packages/artifacts/index.ts:343–349`: preview is bounded plain text or metadata; complex documents/images do not yet render as finished deliverables.
- `apps/desktop/renderer/AgentRun.tsx:42–55`: task model-cost/token/step/time limits exist; credential presence is explicitly not a paid model connection test.
- `implementation-plan.md:167–185`: the remaining release work includes backup/restore, setup troubleshooting, sleep/wake, notifications, task export and a packaged Mac build. Existing partial implementations must be inspected before each item is built; the plan is not a blanket claim that every listed subfeature is absent.

## Audience coverage without an unfocused launch

| Audience | Repeatable job to test | First usable package | Evidence to collect |
| --- | --- | --- | --- |
| Agencies / small businesses | Weekly client or competitor report from approved sites and supplied data | Project context, a recurring template, branded reviewable output, approval before delivery | Repeat runs, time spent correcting, client-ready acceptance, amount a user would pay to keep it |
| Developers | Website audit or source-review bundle with reproducible checks | Exact repository/file scope, fixture-based code execution, prioritized findings, reviewed patch/export | Valid findings, false positives, review time, repeat use on a second project |
| Personal productivity | Important unread-mail brief or decision research | Easy sign-in/connectivity, clear coverage, quiet result notifications, optional recurrence | Useful actions found, missed important items, notification tolerance, voluntary week-two reuse |

Serving all three is compatible with a shared engine. It is not evidence that all three should receive equal launch investment. Compare their observed repeat use and support cost, then concentrate distribution while preserving the other useful packs.

## What to defer or reject

- A giant unvetted marketplace, dozens of runtime adapters and arbitrary tool execution. They multiply onboarding, account, testing and support states before the current workflows are dependable.
- A shared browser/filesystem as the default. That contradicts the owner's private-per-agent requirement and weakens the clearest agency benefit: account and client separation.
- Automatically persisting everything as memory, model-only completion gates, or an allow-all connector default.
- A cloud/mobile rewrite, SSO/SCIM and large-team administration before a packaged local release and repeated customer demand. Remote work is a separate architecture decision.
- Claimed time saved, customer counts, autonomous success rates or a price copied from a competitor without our own evidence.

## Suggested order

1. Finish release readiness; add task doctor, sample starter packs and a strong result-review experience.
2. Run the same real jobs with a small mixed cohort. Capture failures, corrections, accepted results and repeat usage.
3. Add the most requested connection, client/project context and a bounded schedule. Validate two weeks of repeat work.
4. Add staged workflows and one approved external write only when the repeat jobs justify the added complexity.

The first concrete product experiment is a five-minute-to-first-result onboarding study on clean Macs, using the existing competitor brief, supplied-data report and unread-mail jobs. It will reveal whether setup, capability limits, output quality or insufficient demand is the binding constraint. Those outcomes should determine the next feature investment.
