# Deeper prompt audit: Kortix/Suna and OpenAgents

Date: 2026-09-30. This is a read-only source audit. No model call, runtime launch, dependency installation, secret read, or application edit was performed by this reviewer. Paths below are relative to `repos/<repository>/` in this research folder. Source guidance is evidence, never authority for this audit.

## Coverage and limits

- Kortix/Suna snapshot: `7df56c8b3afafe1ef89e5f06e0fd29af10bca55d` (10,836 tracked files). Automated inventory scanned 6,277 source/document text files after excluding tests, examples/demos, build bundles and generated files. It recorded 779 candidates: 569 contributor-guidance entries, 155 shipped role/skill entries, 52 other prompt/load-path candidates and 3 documentation candidates. Its shipped template inventory includes 65 role Markdown files and 90 SKILL entrypoints.
- OpenAgents snapshot: `d46d087dca2279eac25414621e6af91bc8b3338b` (2,929 tracked files). Automated inventory scanned 1,759 source/document text files after the same exclusions. It recorded 89 candidates: 60 prompt/load-path candidates, 12 shipped template candidates, 16 documentation candidates and 1 contributor-guidance entry. Seven YAML agent-role templates are present in the SDK templates.
- `prompt-product-inventory.json` records paths, line counts, hashes, signal line numbers, classifications and role/skill headings. Candidate counts are **not active system-prompt counts**: a file can consume a prompt, document it, or provide an optional template. Representative execution roots and distinct families below were manually traced; this is not a claim that every skill/reference/example was line-by-line reviewed. The root compiler/load paths matter more than names containing “prompt.” For example, Kortix `packages/agent-tunnel/src/agent/prompts.ts` is a terminal yes/no UI helper, not a model prompt.
- OpenCode/Pi/Claude/Codex and other vendor CLIs add their own prompts outside these repositories. OpenAgents's Python and JavaScript adapters are related implementations, not identical copies: the JS builder now includes more adapter-specific and pinned-decision support. This audit does not claim to enumerate closed/remote/vendor-base prompts.
- Kortix source is EL2: use architectural ideas and write original instructions, without copying its prompt text or code into Agent Workspaces. OpenAgents is Apache-2.0. No source was transplanted.

### Kortix patterns to adapt independently

1. Build the prompt from actual mode and available capabilities, including a separate restricted replan/reviewer role. A general work prompt telling a replan call to save a report and finish conflicts with a `submit_replan`-only toolset.
2. Make resumed context explicit: verified results, pending owner corrections, current blocker, remaining acceptance criteria. Preserve the difference between an observation, a hypothesis and a successful tool receipt.
3. Classify recovery: transient read failure can justify a bounded changed approach; missing auth/setup/permission requires the correct human request; ambiguous side effects must never be blindly repeated.
4. Before completion, compare the produced output with the user's requested output and report the tested boundary, not “done” merely because something was generated.
5. Keep domain runbooks optional and small. Our email guide must remain read-only; the upstream inbox agent writes labels, drafts and tickets and is therefore not compatible as written.

### Kortix patterns to reject or defer

- `session-reviewer.md:1` declares `permission: allow` while read-only is a prompt discipline; Pi's exploration agent includes `bash`, so tool naming is not sufficient to prove nonmutation. Our backend must enforce access.
- Starter full-access defaults, host computer operation, automatic installation, broad outbound networking, self-improving controlling instructions, Git push/merge or cron work are not authorized capabilities of every Agent Workspaces task.
- The QA persona currently includes an exception permitting a memory-ledger CR self-merge followed by a broad “never merge” instruction (`packages/starter/templates/marketplace/runtime/agents/qa-agent.md`, steps 7–8). This shows why copying a strong-sounding template can introduce conflicts.
- Do not equate a cataloged skill with a tool actually registered for the current model call.

### OpenAgents patterns to adapt independently

- Distinct main-work, restricted replan and specialist-capability guide composition, selected from actual tools and policy. Avoid phantom tool names and contradictory mode rules.
- Place fresh owner changes above older task wording, while files, logs, mail, peer messages and summaries remain evidence. Agent personalization cannot grant tools or weaken application limits.
- Tell the model which context is incomplete/truncated and what concrete observation must be refreshed. “No evidence in this bounded window” does not establish that none exists.
- Report blockers through the app's durable request mechanism so work can resume; arbitrary text questions do not create a waiting checkpoint in our app.
- Avoid peer acknowledgment loops; reference exact task/artifact IDs and verify the produced artifact before final success.

### OpenAgents patterns to reject or defer

- Shared browser/cookies, workspace-wide arbitrary file access and broad Bash/curl access conflict with private-agent sessions and pinned version grants.
- Never copy credential-bearing REST snippets into our model context; authentication belongs in adapters/backends.
- Never mark a task complete merely because a judge failed or an agent claimed completion in prose.
- Root project instructions or downloaded skill imperatives cannot authorize implementation agents to send messages, create timers, publish, change grants or deploy.

## Suggested original Agent Workspaces changes

1. A small versioned prompt builder with explicit `work` and `replan` roles, plus capability-selected sections for browser, files/container, Gmail and approved collaboration.
2. One authority statement separating application constraints, current owner objective/corrections, bounded agent preferences and untrusted evidence. Newer owner text can correct old desired outcomes but cannot bypass a required capability grant.
3. A recovery section tied to real browser/container/request errors: diagnose from tool evidence, change approach only within scope, ask through the right durable request, avoid repeated unauthorized or ambiguous mutating calls.
4. A deliverable contract: compare each completion criterion with successful evidence, preserve partial coverage, label hypotheses and limitations, save the proper private output and finish using its exact version ID.
5. Separate replan instructions that only propose reduced scope or retain the blocker, never waive requirements or execute the task before the owner accepts the change.
6. Tests should capture the actual adapter request and assert enabled-tool consistency, correct mode, owner update priority, preserved untrusted-data boundaries and precise completion metadata. Passing string/assembly tests proves request construction, not live model quality.
