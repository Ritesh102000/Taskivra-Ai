CHAPTER 01 / START HEREStart here: what this product does

A plain-language introduction before you touch any settings.

A simple example · What the application name means · Desktop application versus this guide website · How to read this guide

Taskivra AI is a desktop application for your Mac. You give an AI helper a piece of work, give it the information and access it needs, and review what it produces. You can have several helpers with different jobs. The application saves their tasks and progress so you can supervise the work.

An agent is an AI helper with a name, instructions, private files, and a browser session. It uses a model - the AI service that reads context and proposes the next step. The application checks those proposed actions before using its tools. A task is one specific job given to an agent.

A simple example

You create an agent called Research Assistant. You give it two company website links and ask it to compare their pricing. It reads permitted pages, writes a report, and asks you if it needs missing information. You review the report and decide whether it is useful. It does not become correct merely because the task says Complete.

What the application name means

This repository is called Taskivra-Ai and this guide calls the product Taskivra AI. The current desktop window and local application still say Agent Workspaces. They are the same project. Storage and internal names have been kept so existing work is not disrupted.

Desktop application versus this guide website

The Vercel website hosts this guide and its PDF. It is documentation, not a cloud version of the application. Your agents, database, files, browser sessions, and Docker jobs run through the local Mac application. Hosted AI providers process the context sent to their APIs.

Current stage

Version 0.9.9 is a local pre-release. Apple Silicon Mac is the validated development platform. A public installer, Windows/Linux support, Intel Mac support, automatic updates, and clean-machine installation have not been validated.

How to read this guide

  • If the app is not installed, start with Install and open the application, then Connect the AI model.
  • If someone has already prepared your Mac, start with Create your first agent, then Your first task.
  • Choose a use-case walkthrough to see exactly what to type and how to review its output.
  • Use the clickable contents, subsection links, and PDF bookmarks to move around. Every ordinary PDF page has a Contents link.

CHAPTER 03 / SETUPInstall and open the application

Prepare a source checkout on a Mac, or open an app that has already been prepared.

If you already have the app · If you are installing from this repository

If you already have the app

  1. Open Agent Workspaces

    Open the local application your developer prepared. It currently uses the older product name. Read any setup status shown in Settings. A window opening does not mean its model, browser, or container tools are ready.

  2. Check the model connection

    Before live work, open Settings and check Models and providers. Continue with the next chapter if no usable connection is configured.

If you are installing from this repository

The repository is source code, not an automatically configured installer. These steps are for the person preparing the Mac. Terminal is the Mac application used to enter the commands below. A beginner can ask a developer to complete this section, then use the interface for ordinary tasks.

  • Use an Apple Silicon Mac, with Node.js 24.14.0 or newer and npm installed. Node/npm build and install the source dependencies.
  • Apple Command Line Tools provide the compiler for the native helpers. Install them with xcode-select --install if missing.
  • Install Google Chrome if ordinary browser tasks will use the dedicated Chrome backend.
  • Install and start Docker Desktop only if code execution or the optional container browser is needed. The local lab browser itself does not need Docker.

  1. Download the source

    Open Terminal in a suitable folder, then run the download and install commands below. npm ci installs the versions recorded by the repository lockfile.

  2. Compile native helpers

    Run the helper commands. They compile the Mac components used for Keychain and the Chrome bridge. They do not sign in, read saved secrets, or connect an account.

  3. Start the app

    Run npm start from the repository folder. It builds the interface and opens Electron, the desktop runtime.

  4. Complete capability setup

    Connect a model. Prepare the selected agent's Chrome profile if needed. Provision the code image if a workflow requires calculations. Each capability has a separate chapter.

git clone https://github.com/Ritesh102000/Taskivra-Ai.git
cd Taskivra-Ai
npm ci
npm run model:setup
npm run gmail:setup
node packages/google-workspace/setup.mjs
npm run browser:native:setup
npm start

Disk space and installation limits

Code-image setup checks for at least 8 GiB free host disk; local app packaging checks for at least 2 GiB. These are separate minimums, not the total space needed. Docker/browser images can use more. Clean-Mac installation and a public signed/notarized distribution are still release work.

If npm or a helper is missing, resolve that setup issue before starting a task. Do not paste API keys or your Mac password into Terminal commands. See Troubleshooting.

CHAPTER 04 / SETUPConnect the AI model

Give the app a supported AI service or a local model server.

Choose cloud or local · Add a connection step by step · Understand task limits

Choose cloud or local

A cloud connection sends task context to a provider over the network and may charge for use. A local connection points to a model server you already run on the Mac. The application does not download models or install Ollama/LM Studio for you.

ChoiceWhat you need
OpenAI or Claude / AnthropicAn API account, exact supported model ID, API key, and current declared prices. A consumer chat subscription is not API access.
Ollama on this MacA running Ollama server and installed model with its explicit tag. Choose a model/server that supports the app's structured tool calls.
LM Studio or another compatible serverA running compatible server, its API base URL, exact model ID, and any authentication it requires.
OpenRouter, Together AI, Groq, LiteLLM, or another gatewayA compatible endpoint, credentials if required, an exact model, and declared metered prices when cloud charges apply.

Add a connection step by step

  1. Open Settings

    Find Models and providers, then choose Add connection. Pause running tasks before changing model connections.

  2. Choose Provider or server

    Use a preset that matches the service. The preset fills some protocol settings; it does not install or test the model.

  3. Enter Connection name and Exact model ID

    Give the connection a name you recognize. Copy the exact model identifier from your provider/server. Do not use a guessed model name.

  4. Check API base URL, Authentication, and Billing

    The base URL is the address of the model service. Remote services require HTTPS. Local HTTP is supported only for loopback. A local gateway that calls paid cloud models should still be metered.

  5. Enter a key and declare prices if needed

    Use the password-style API key field. Metered connections need input/output prices per million tokens. Check current prices with your provider rather than treating an example as a live quote.

  6. Review per-call token limits

    Reserved input tokens per call is the allowance reserved before a request. Maximum output tokens per call limits the answer. Keep both within the model's capacity.

  7. Confirm structured tool support and save

    Confirm that the chosen model supports structured tool calls, then select Save connection. The app says no model request was sent.

  8. Select this model for the task

    When preparing a task or fleet, choose the saved connection. A small harmless first task can reveal account/protocol problems; it is live use and may cost money.

Understand task limits

LimitWhy it matters
Model spendMaximum declared model spend allowed for the task. Settled usage plus uncertain reservations count.
Model callsHow many model generation attempts the task may use.
Tool stepsHow many tool actions it may perform.
Total tokensThe task's input/output token budget.

Configured is not tested

Supported protocols are OpenAI Responses, Anthropic Messages, native Ollama chat, and compatible Chat Completions. The current contract supports text and at most one valid client tool call per turn. Some model dialects are incompatible. Saved settings do not prove a working account/server. Editing a connection creates a new revision; saved tasks retain the previous revision.

Keys are stored in macOS Keychain. Unknown provider outcomes retain a budget reservation and are not blindly retried. Declared-price accounting is local; invoices and gateway fees can differ. See Data and recovery.

Create a project first when you need separation

  1. Open Projects

    A project keeps a client or topic's shared files, task membership, and coordination separate. You can use the existing personal workspace for a first simple task.

  2. Create project

    In New project, enter a Name such as Practice workspace and an optional Description. Choose Create project.

  3. Add an agent inside that project

    Use its Add an agent form to create the helper in the correct project. Existing agents cannot currently be moved between projects.

Create an agent from the main agent list

  1. Choose the plus beside YOUR AGENTS

    This opens Create an agent. For client-specific work, use the project's Add an agent form instead so membership is explicit.

  2. Enter Agent name

    Use a job-oriented name such as Research Assistant, Data Analyst, or Mail Assistant. The name does not grant tools or account access.

  3. Enter Instructions

    Describe its normal working style and constraints. This is reusable guidance, not the particular task. Instructions are optional, but clear ones make the purpose easier to review.

  4. Choose Create agent

    The helper appears in the agent list with a private workspace. Creating it does not launch a paid model task or sign in a browser.

A copyable instruction example

Work carefully and explain your sources.
Ask me when essential information is missing.
Distinguish observed facts from assumptions.
Do not claim to have read content you could not access.
Write a clear result with limitations and next steps.

What is separate for each agent

  • Private task files and outputs are scoped rather than shared automatically.
  • Browser cookies and tabs belong to the agent session/profile, not your personal browser.
  • Tasks have their own objectives, model selections, access, and limits.
  • Publishing a file is an explicit way to let approved project peers use an exact copy.

Keep secrets out of instructions

Do not put your API key, Google password, Mac password, or personal browser cookies here. Use Settings and direct sign-in when a connection or login is needed.

CHAPTER 06 / EVERYDAY USEGive an agent its first task

Turn a vague request into a saved job you can inspect and run.

The easier route: a workflow · The manual route: New task · How to write a useful objective · How to define done · Understand progress states

The easier route: a workflow

  1. Open Workflows

    Select a starter that matches the job, such as Compare competitors, Compare two CSV files, Review code files, or Review unread Gmail.

  2. Choose Use workflow

    Read the requested fields and enter the job-specific information. A workflow is a form plus a saved procedure, not a guarantee of a good result.

  3. Choose the project agent and model

    Select the helper that should do the job and its configured model. Review the permissions and budget controls shown.

  4. Review task, then Save task

    Review the prepared objective, criteria, and allowed access. Saving prepares the job; it does not mean the model has completed it.

  5. Resolve readiness

    Open the saved task. Assign required files or configure the missing browser, model, or account. Readiness reports what is missing.

  6. Choose Run agent

    This starts live model calls and permitted tools. Keep the app available. Inspect Activity as it works.

  7. Respond when it needs you

    Open the request, answer only the missing information, or complete browser/account setup. Paused or cancelled work stays under your control.

  8. Review Results

    Open the exact output and check its sources and coverage. Accept it if useful, or request changes with a precise correction.

The manual route: New task

Use New task on the selected agent when no starter fits. Choose Live agent for real model/tool use, enter What should the agent accomplish? and What does done look like?, select the model, and review access/limits. Save live task, then resolve readiness and run. Live mode is different from Simulation.

How to write a useful objective

Compare the public pricing pages I approved for Company A
and Company B. Summarize the plans, important differences,
and any information you could not verify.

How to define done

A private Markdown report with a comparison table,
links to the pages actually read, uncertainties,
and three questions I should investigate next.

Simulation uses scripted local scenarios such as asking clarification, completing, or failing. It makes no model calls. It does not demonstrate that a live AI has performed the same work.

CHAPTER 07 / EVERYDAY USEFiles and human requests

Give the right inputs without sharing your whole computer.

Import a private file · When the agent requests a file · Clarification and reduced scope · Publish only when another agent needs the file

Import a private file

  1. Open the intended task

    Choose the job that should use the file. Importing into an unrelated task does not grant this job access.

  2. Use the file picker or supported file drop

    Select only the files needed. The app imports managed copies and validates format/size. Agents do not browse arbitrary host folders.

  3. Check the saved version

    A version is the exact imported copy. Later edits to the original file on your Mac do not silently change it.

  4. Assign named workflow slots if present

    In Activity, open Ready for this job? and Assign the files for this run. Give each required slot the correct version, such as the earlier and later CSV. Read the validation result.

When the agent requests a file

  1. Read the request and slot names

    A slot explains the particular file or format needed. Do not assume any file satisfies it.

  2. Supply the requested input

    Choose a matching file through the owner interface. Do not paste a local file path as a substitute for importing the content.

  3. Resolve rejected slots

    A wrong format or missing slot remains blocked. Replace the rejected input; already accepted slots remain saved.

  4. Review continuation

    Once all required inputs are fulfilled, the eligible task can receive one continuation from saved progress. An owner pause or cancellation is not overridden.

Clarification and reduced scope

A clarification request asks a question such as which date range to analyze. Answer with the specific missing information. If the agent cannot complete the original scope, it can ask you to accept a smaller scope. The application requires your acceptance rather than silently calling incomplete work done.

Publish only when another agent needs the file

A private output stays private until deliberately published. Publish an exact project version, then authorize a peer task to consume it. The shared library is a project sharing area, not a public website. If you publish a later copy, tasks already using the earlier version keep their original evidence.

Bounds and supported formats

Default import bounds include 100 MiB per file, 250 MiB per batch, and 32 files per batch. A workflow, preview, Google import, or fleet can impose smaller limits. PDF/XLSX extraction uses a separately prepared document image and supports ordinary bounded files; it does not run macros or perform OCR.

  1. Install Chrome and compile the bridge

    Chrome is expected at /Applications/Google Chrome.app. The source helper is built with npm run browser:native:setup.

  2. Open the selected agent's Browser setup

    Prepare its dedicated profile, then select Open Chrome setup. Use that agent's Chrome window, not your personal profile.

  3. Open chrome://extensions

  4. Return to the app and refresh status

    The bridge connects that particular agent profile. Each new profile needs its own extension setup.

  5. Reload after changing extension source

    Close the task browser, Reload the extension in its Extensions page, then reopen the browser. Rebuilding the app alone does not reload an unpacked extension.

Take control for login

  1. Open the agent browser

    Inspect the task's browser state. If the task requests login, read which account/site it needs.

  2. Choose Take control

    The app transfers exclusive control to you. Use the actual dedicated Chrome window for navigation, password entry, and MFA.

  3. Finish the intended login

    Credentials stay out of task messages and saved page traces. Do not import your personal Chrome profile or enable personal profile sync.

  4. Choose Return to agent

    The app adopts allowed relevant tabs and requires a fresh observation before agent actions resume. The task still respects its allowed sites and saved scope.

Can you work while the agent works?

Ordinary agent operations use their managed tabs rather than the Mac's global mouse/keyboard. You can use your own browser while agents work in separate sessions. Explicit inspection/takeover can bring the agent window forward. Human takeover blocks agent reads, previews, and inputs until you return control.

Login compatibility is not guaranteed

A dedicated Chrome profile separates cookies from your personal browser, but it is not a container/network sandbox. A site can still reject login or ask additional checks. Gmail has a supported read-only OAuth alternative. Native managed upload/download is unavailable; manual downloads do not automatically become task inputs.

There are two active browser slots and up to six managed tabs per session. Backends do not migrate cookies when switched. For Google accounts see Google connections.

CHAPTER 09 / SETUPUnderstand the code and command tools

Calculations happen in isolated jobs, not an unrestricted terminal on your Mac.

Prepare the code runtime · What the agent can and cannot reach · The lab command tool is different

Some tasks need calculations or file transformation. Python and Node.js are programming runtimes; shell is a command language. The app can execute these inside a disposable Docker container. A container is a separate execution environment with bounded resources.

Prepare the code runtime

  1. Install and start Docker Desktop

    Docker must be running before the app can prepare or launch jobs. The app does not install it automatically.

  2. Explicitly provision the portable image

    On a fresh Apple Silicon Mac, run the command below. Network access is allowed during this owner-controlled image build, not during agent payload jobs.

  3. Check readiness

    Run npm run code:check and resolve the reported issue if not ready.

  4. Run only an authorized task

    The task receives verified snapshots of approved input versions. It can create bounded work/output files; exported files are verified before commitment.

node packages/code-runtime/setup.mjs --build \
  --bootstrap-base --allow-network
npm run code:check

What the agent can and cannot reach

  • Jobs run offline with no task-time network. They do not receive host folders, browser cookies, model keys, or the Docker socket.
  • Standard images have Python/Node standard libraries. Additional packages require a reviewed pinned dependency recipe.
  • Default job limits include one CPU, 1 GiB memory, a 120-second payload deadline, and bounded logs/output.
  • Stop interrupts the owned container and fences late output commitment. A clean exit alone is insufficient; export must also verify.

The lab command tool is different

In the local website fleet, lab_command accepts a small curl-shaped JSON request to the same verified training site. It performs one bounded HTTP request using that agent's synthetic session. It does not start a host shell, execute the Mac's curl, read host files, or contact arbitrary targets. Offline code in that mode can process permitted fleet reports only.

Fresh setup distinction

npm run code:setup is the older offline build path and expects the exact retained Phase 0 base. A missing base on a new machine requires the explicit portable provisioning command above. The optional container browser has a separate setup gap.

CHAPTER 10 / TEAMWORKShare work and coordinate agents

Understand what becomes visible and how handoffs stay reproducible.

Private first, shared deliberately · Ordinary coordination versus Fleets

Private first, shared deliberately

Agents do not automatically see each other's private files, objectives, browser pages, or unpublished outputs. A project gives them a shared library, task awareness, and scoped inboxes. Publishing and task authorization decide what evidence another agent can use.

  1. Produce or import the source

    Keep it in the relevant project/task. Check that it contains only what the peer needs.

  2. Publish its exact version

    This creates a shared immutable project copy. Publish does not upload it to the public internet.

  3. Select that version for the receiving job

    The peer works from the pinned copy. Describe what it should do with it and define a useful output.

  4. Use messages for coordination

    Send scoped status/findings through the permitted coordination surface. General messages primarily share references and summaries; they do not automatically grant private file or browser access.

  5. Review dependencies

    A dependent task needs the upstream work to complete. Cycles and unfinished/failed upstream dependencies remain visible rather than being treated as satisfied.

  6. Review the handed-over output

    Record exact report versions and source coverage. Do not assume a peer message proves a conclusion.

Ordinary coordination versus Fleets

Ordinary agents can coordinate within authorized peers/projects. Fleets add an automatically organized bounded lead-and-specialist workflow. A fleet lead plans items and dependencies, workers exclusively claim eligible work, scoped messages carry bounded finding text, and exact completed reports are staged for the lead or dependent workers.

Version pinning matters

If a report changes tomorrow, yesterday's task does not silently consume the new report. A new input selection or handoff records the intended exact copy. This makes it easier to reproduce what each agent actually saw.

For a single objective handled by a team, continue with Understand Fleets.

CHAPTER 11 / SETUPGoogle accounts: Gmail, Drive, and Sheets

Connect explicitly and understand exactly what is read.

Why Gmail uses a separate connection · Connect Gmail step by step · Basic and detailed mail reads · Selected Drive and Sheets imports

Why Gmail uses a separate connection

Google can reject sign-in inside an embedded automated browser. The supported Gmail path uses a Desktop OAuth connection: you sign in and consent in the system browser, then the app reads through a bounded API. OAuth means granting a specific application permission without placing your Google password in a task.

Connect Gmail step by step

  1. Prepare your Google Cloud project

    In Google Cloud Console, create/select the project that will own this connection. Enable Gmail API.

  2. Configure the consent audience

    Set up app branding/contact details and the appropriate audience. If it is in Testing, list the exact intended Gmail address as a test user.

  3. Choose the read-only scope

    Configure gmail.readonly. The app has no Gmail send, archive, delete, modify, or mark-read operation.

  4. Create a Desktop app client

    Create an OAuth client with application type Desktop app and download its JSON. A Web client or service-account key is not the required format.

  5. Prepare and save the Gmail task

    Open Workflows > Review unread Gmail > Use workflow. Select the intended agent, enter your exact Gmail address and what matters to you, choose a configured model, and review the limits. Choose Review task, leave detailed review disabled for a headers-and-snippets brief, then choose Save task. A saved live task naming the account is required before Connect Gmail becomes available. Saving does not read mail or start model calls.

  6. Import and connect in Settings

    In Settings > Gmail connection, import the JSON through the native picker. If several saved mail tasks exist, select the intended Saved Gmail task. Choose Connect Gmail and complete sign-in/consent in the system browser with the exact account saved on that task.

  7. Verify the account and approve project use

    Choose Verify account for project use, then open Projects and select the project containing the agent. Under Approved accounts > Gmail, choose Approve followed by the verified address. The exact account must match the saved task/project requirement; a different account cannot release that blocker. After restart, Verify account checks identity without listing mail. Return to the saved task and check its readiness before choosing Run agent.

Selected Drive and Sheets imports

Drive/Sheets use a separate connection and separate project account approval. Enable the relevant APIs, import a Desktop client through the Google-inputs flow, and choose one exact supported file or finite named-sheet A1 range. The app imports an immutable local snapshot with source identity, retrieval time, hash, and omissions. It does not modify or continually synchronize the source.

Account permission versus selected resource

The current Drive read-only OAuth scope is broad. The application broker restricts which selected resource it imports; it is not a Google-issued per-file grant. Gmail tokens do not grant Drive authority. The original downloaded client JSON remains where you saved it, so keep it private.

Expired or revoked authorization requires reconnection. Provider setup/verification for a widely distributed app is separate release work. See the email walkthrough for a copyable first task.

CHAPTER 12 / EVERYDAY USEReview results and repeat useful work

Completion, acceptance, export, and scheduling mean different things.

Review the result · Choose an export · Save a reusable workflow · Set up a routine carefully

Review the result

  1. Open Results or the completed task

    Read the exact output version, rather than only the progress summary.

  2. Read coverage and evidence

    Check which pages/files/messages were read and what was omitted. Confirm important assertions against their sources.

  3. Inspect quality checks

    They can catch malformed JSON/CSV, missing required headings, empty output, or receipt references outside the task. Passing does not prove facts or calculations.

  4. Accept or request changes

    Accept records your judgment. If something is wrong, ask for a specific correction and retain the original version history. Fleet result revisions follow their own scoped workflow.

  5. Export if needed

    Use the available exact-original export or a supported formatted report export. The native save dialog selects a destination and refuses replacement of an existing file.

CHAPTER 14 / REFERENCEData, privacy, pause, and backup

Know what stays on the Mac and what can leave it.

Where work is saved · What a model receives · Create and verify a backup · What automatic recovery handles

Where work is saved

The default persistent root is ~/Library/Application Support/Agent Workspaces. SQLite stores task/run history, requests, receipts, usage, projects, and fleet state. Managed directories store exact artifacts and workspace revisions. This local data is not the public source repository.

What a model receives

A hosted model receives the selected task context and authorized content needed for its requests. A local model server processes requests through the chosen endpoint. Private by default refers to app sharing boundaries; it does not mean content is never sent to a configured cloud provider.

  • Model API keys and Google connection/client tokens use macOS Keychain and are excluded from ordinary task files and portable backups.
  • Native Chrome manages its own dedicated profile storage; container browser checkpoints are encrypted. They are different stores.
  • Files and messages you supply can contain secrets. The app does not automatically redact every possible sensitive item.
  • Local portable backups contain private tasks/files and are not encrypted or content-redacted. Keep them private.

Create and verify a backup

  1. Open Settings: Backup and recovery

    Choose Create backup. This pauses work while the app makes a verified copy.

  2. Choose a new destination in the Mac dialog

    The app writes to a new child location and refuses replacement. Keep the backup somewhere private with enough space.

  3. Use Check backup

    Verification checks exact hashes, referenced files, database integrity, and foreign-key consistency.

  4. Restore to new folder when needed

    Restore creates a new verified location; it does not overwrite the active workspace or automatically switch to it. Credentials and browser logins are not transferred.

  5. Review before reactivating

    Restored tasks and routines stay paused/disabled until reviewed. Accounts and browser sessions require appropriate fresh setup.

What automatic recovery handles

The recovery service can retry transient browser observations within durable finite allowances. It does not blindly retry login/MFA, paid model requests, uncertain navigation, clicks, or other writes. Inspect Automatic recovery for the saved history. Acknowledge marks an incident reviewed; it does not reset its retry allowance.

Protected system prompts

Complete macOS Keychain access dialogs yourself after reviewing them. Do not send your Mac password to an agent or paste it into messages. Rebuilt apps can be treated as changed by macOS.
